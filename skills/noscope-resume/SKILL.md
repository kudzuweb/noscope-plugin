# noscope-resume

You are the Incident Commander of the incident whose run folder `F` the invocation names
(without one, `node ${CLAUDE_PLUGIN_ROOT}/scripts/incident_current.mjs` prints it for the current directory). Every fact you need is in the record; nothing is
carried by memory from any earlier session. `S` is `${CLAUDE_PLUGIN_ROOT}/scripts`.

| Step | What you do |
|---|---|
| 1. Orient | Read, in full, once: `${CLAUDE_PLUGIN_ROOT}/references/noscope-protocol.md`, what `node ${CLAUDE_PLUGIN_ROOT}/scripts/incident_orient.mjs ic` prints, `${CLAUDE_PLUGIN_ROOT}/skills/noscope-run/role.md`, and `${CLAUDE_PLUGIN_ROOT}/skills/noscope-run/SKILL.md`, which is the cycle you will continue. |
| 2. Decide whether there is anything to do | Read `$F/incident.json` and `$F/run.json`. `satisfied` or `failed`: run section 8 of `/noscope-run` (review and report) if `$F/morning-report.md` is missing, `CronDelete` any `heartbeat.cronId`, and stop. `stopped` (a human stopped it): resume only because a human asked you to, in words, in this session; then `node S/incident_apply.mjs run $F/incident.json paused null` and set the status back with the command turn. `blocked` with an unanswered question: in an attended run ask it in the conversation and record the answer with `node S/incident_apply.mjs answer`; in an unattended run write the morning report if missing and stop. Past `cutoffAt` in `mode: cutoff`: write the morning report if missing, `CronDelete` the heartbeat, and stop; the incident stays open. Otherwise continue. |
| 3. Take command | `node S/incident_session.mjs join $F` first: it marks this session a seat of the run, and until it is marked the plugin's hooks do not fire here, so nothing would log your turns or push the cycle along. Then `node S/incident_brief.mjs ic $F/incident.json --whole`: the change since the last command turn and the whole state, since this session has not read it before. Read the newest `$F/handoff.json` if one exists; it is the last IC's reading and binds you no more than a briefing does. Clear the pause: `node S/incident_apply.mjs run $F/incident.json paused null`. Call `ListAgents` once to learn this session's name; record it as the IC: `node S/incident_apply.mjs run $F/incident.json icSession '"<your name>"'`, and add it to `sessions`: `node S/incident_apply.mjs run $F/incident.json sessions '<the list plus "<your name>">'`. |
| 4. The leaders | Leaders are sessions of their own and usually still running. For each active unit, `ListAgents`: if ``$(node S/incident_name.mjs $F leader <unit-id>)`` is listed, `SendMessage` it one line, `command is now with <your name>; reply when you have read this`, and wait for the reply. If it is not listed (the machine restarted, or the tab was closed), relaunch it: `bash S/launch-session.sh leader $F <the unit's leader model id> `$(node S/incident_name.mjs $F leader <unit-id>)` <unit-id>`; the launcher waits for it to come up and exits non-zero if it never does, and prints what it tried, why the tab stopped if it got far enough to say, the command a human could run, and that the decision is yours. Read the reason first: an overloaded provider is worth waiting out and launching again; an authentication failure is a question for the human, not a retry. Make it: in an attended run give the human the command and go on without the seat; in an unattended run close the unit or reassign its slice at your next turn, and say which and why. Either way do not wait on a check-in that will not arrive; once up it orients itself from the record, which carries the unit's tasks so far and its last picture, and reports up. A task that was `running` when the last session died and has no result in the record is spawned again by its leader with the same brief (`node S/incident_brief.mjs task $F/incident.json <task-id>`), and `apply start` records the new start; it did not fail, so nothing is recorded against it. |
| 5. The heartbeat | In an unattended run, if `run.json` has no `heartbeat.cronId`, `CronCreate` one: every `heartbeat.everyMinutes` minutes (15 by default), prompt `Run /noscope-resume <F>`, and record its id with `node S/incident_apply.mjs run $F/incident.json heartbeat.cronId '"<id>"'`. A tick that finds the run live (the loop hook is pushing the cycle along and `incident_next.mjs` has work in flight) does nothing but say so in one line; a tick that finds work due and this session idle continues the cycle, which is the tick's purpose beside restarting a dead run. |
| 6. Continue | `node S/incident_next.mjs $F/incident.json` and go on from section 4 of `/noscope-run`. |
