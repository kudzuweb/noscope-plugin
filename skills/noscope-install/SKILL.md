# noscope-install

Everything the plugin needs that installing it does not give it. Each step checks first and
changes only what is missing, with the human's consent for any edit to `~/.claude/settings.json`.

| Step | Check | If missing |
|---|---|---|
| 1. Prerequisites | `node --version` is 18 or later; `jq --version` answers; `git --version` answers, because the first incident runs `git init` in the records folder and the directing session commits the record at every turn. | Say which is missing and how to install it: `brew install node jq git` on a Mac, the distribution's package manager on Linux (`apt install nodejs jq git`, `dnf install nodejs jq git`). Stop until all three exist. |
| 2. The plugin is enabled | `echo "$CLAUDE_PLUGIN_ROOT"` prints a path. That is the one test that covers both an install and a `--plugin-dir` load, and it is what every later step needs; `claude plugin list` showing `noscope` confirms an install specifically. | Read the Install section of `${CLAUDE_PLUGIN_ROOT}/README.md` and give the human its two commands verbatim, with the absolute path filled in; never compose an install command yourself. Stop until it is enabled. |
| 3. The status line sensor | The compaction guard reads `~/.claude/.handoff-state/<session>.pct`, which a status line writes. Run `echo "$CLAUDE_PLUGIN_ROOT"` and use that literal path everywhere below — never write `${CLAUDE_PLUGIN_ROOT}` into `~/.claude/settings.json`, which is the user's file and has no plugin to resolve it against. Read `~/.claude/settings.json`. Case A: `statusLine.command` is unset. Case B: it names a script; read that script and look for a line writing to `.handoff-state/` with `.pct`. | **A:** copy `<plugin root>/statusline/noscope-statusline.sh` to `~/.claude/noscope/statusline.sh` and `chmod +x` it, then propose `"statusLine": {"type": "command", "command": "bash \"$HOME/.claude/noscope/statusline.sh\""}` and on consent write it. Copy rather than point into the plugin: the plugin's path carries its version (`.../noscope/0.15.1/`), so a `claude plugin update` would leave the status line aimed at a directory that is pruned, and the guard would die silently. The copy needs nothing from the plugin to write the sensor file. **B, sensor absent:** propose appending this to that script, on consent, changing nothing else in it — `INPUT` is whatever variable that script already read its stdin into, which you must find and name, because stdin is consumed once: <br>`sess=$(printf '%s' "$INPUT" \| jq -r '.session_id // empty')`<br>`p=$(printf '%s' "$INPUT" \| jq -r '.context_window.used_percentage // empty')`<br>`if [ -n "$sess" ] && [ -n "$p" ]; then d="$HOME/.claude/.handoff-state"; mkdir -p "$d" 2>/dev/null && printf '%s' "${p%.*}" > "$d/$sess.pct" 2>/dev/null; fi`<br>**B, sensor present:** nothing. **Then prove it, in every case:** `ls ~/.claude/.handoff-state/` after the next status-line render, and read one file — it holds a number. No file, or an empty one, means the sensor is not installed however the edit went, and the guard will never fire. Say which case you took and what the proof showed. |
| 4. The configuration | `~/.claude/noscope/config.json` exists with `workStarts`, `handoffThreshold` and `incidentsDir`. | Ask, in one call of the question tool: where incident records go (default `~/Documents/Projects/noscope-plugin-incidents`; a git repository is created there on the first incident if none exists, one folder per project and one per incident), what time work starts (default 09:00; the cutoff for an overnight run is five hours before it), the context percentage at which an IC session hands off (default 75), and the model for each seat above a task, each answered with one of the four ids in `AVAILABLE_MODELS` (`scripts/incident_lib.mjs`) — `claude-fable-5-1`, `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5` — or `smallest`. Nothing validates this later: a name that is not one of those reaches `claude --model` in a launched tab and the tab dies. The seats: the Incident Commander (default `claude-sonnet-5`), the unit leaders (default `claude-sonnet-5`), and the planner (default `claude-opus-5`). `smallest` means the size-up judges, per incident, which available model is right-sized for that role, and the run takes its judgment. Write `{"incidentsDir": "<path>", "workStarts": "HH:MM", "handoffThreshold": N, "usageWindowHours": 5, "icModel": "…", "leaderModel": "…", "plannerModel": "…"}`. Say that the first incident makes that folder a git repository if it is not one already, and creates it if it does not exist; `incident_init.mjs` does this unconditionally, so do not offer a choice the code does not honour. |
| 5. Unattended permissions | `~/.claude/noscope/config.json` has `preAccept`. Absent means off, and off is the default. | Ask, on its own, never bundled into the configuration question, because it is the one answer that gives something away. Say plainly what yes does: for each repository an incident runs on, the plugin writes `hasTrustDialogAccepted`, `hasClaudeMdExternalIncludesApproved` and `hasClaudeMdExternalIncludesWarningShown` into `~/.claude.json`, which are the flags the folder-trust dialog and the external-`CLAUDE.md` dialog write when a human clicks them. It does this so a tab launched while nobody is watching runs instead of sitting on a dialog all night. Say what no costs: every launched session waits for you to click its dialog, so an unattended run stalls at the first one, and an attended run costs you a click per new tab. Say who it applies to: only the working directory an incident names, not every folder. Write `"preAccept": true` on a yes and `false` on a no, and say which you wrote. |
| 6. The terminal | Which terminal is this, and can it be driven from a script? Read `$TERM_PROGRAM`, then look for what that terminal offers: a CLI on `PATH`, a URI scheme, an AppleScript dictionary, a config directory it watches. `~/.claude/noscope/open-tab.sh` already existing and executable means a previous run settled this; say so and do nothing. | **Scriptable:** write `~/.claude/noscope/open-tab.sh`, `chmod +x` it, and say which mechanism you used. It is called as `open-tab.sh <working-directory> <command> <session-name> <colour>` and has one job, to open a tab running `<command>` in `<working-directory>`; it must not wait for the session, which the launcher confirms itself. Test it before saying it works: run it on a command that writes a file, and check the file appears. **Not scriptable** (no interface, or a remote or multiplexed session you cannot address): write nothing, and say plainly that tabs are manual on this machine — every seat that would open one prints the command instead and hands it to you, and the incident runs the same way with you placing the tabs. Never leave a half-written adapter behind; a launcher that calls a broken one is worse than no adapter, since the built-in Warp path is skipped once the file exists. **Warp on a Mac and no adapter:** nothing to do, the launcher already handles it. |
| 7. Verify | `node ${CLAUDE_PLUGIN_ROOT}/scripts/incident_orient.mjs ic` prints an orientation: that is what every seat reads before it does anything, so a machine where it fails has a plugin no seat can start on. Run it for `ic`, `leader`, `planner`, `sizeup` and `task`; each must print, and none may be empty. Then `claude plugin details noscope` lists the skills, agents and hooks that loaded, which is the real inventory check; `claude plugin validate ${CLAUDE_PLUGIN_ROOT}` passes too, though it only checks the marketplace manifest beside `plugin.json` and says nothing about skills, agents or hooks; `bash ${CLAUDE_PLUGIN_ROOT}/tests/scenario.sh` prints `PASS`. | Report the failing step verbatim; the plugin is not ready until both pass. |
| 8. Say what is true now | One table: prerequisites, plugin, orientation (assembles for all five seats, or which failed), sensor (which case), unattended permissions (on or off, and what that means for a launched tab), the terminal (automatic or manual, and by what mechanism), configuration values, tests. Then the one sentence to start an incident: `/noscope-run <objective>` in a session on the repository. | |

A hook the plugin registers (`Stop`, `PreCompact`, `SubagentStop`, `PreToolUse`,
`PostToolUse`, `SessionStart`) needs no step here: plugins register their hooks when enabled,
and every hook is silent outside a folder with an open incident.
